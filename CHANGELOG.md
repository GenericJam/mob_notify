# Changelog

All notable changes to **mob_notify** are documented here.

Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Versioning: [SemVer](https://semver.org/spec/v2.0.0.html).

---

## [Unreleased]

### Changed

- **Docs: the delivered `{:notification, notif}` shape** (MOB-315, MOB-316,
  MOB-178). The moduledoc, README and AGENTS.md describe mob's
  `Mob.Notification` map: `presentation: :foreground | :tap`, `action`, `source`,
  `id`, `title`, `body`, `data`; which process receives it; and that the tap
  that cold-launches the app arrives once. AGENTS.md no longer says Android
  delivery runs through `MobFirebaseService`, which mob_new no longer
  generates.
- **Upgrade step for apps with their own `MobFirebaseService`** (generated by
  mob_new 0.1.45–0.4.10): on mob 0.9.8 a foreground push it hands to
  `MobBridge.nativeDeliverNotification` without `presentation` arrives as
  `:tap`. Add `"presentation": "foreground"` to that JSON (both the
  `mob_notification_json` string and the object it builds). Android
  `:foreground` arrivals of local notifications need mob_new 0.6.3's
  templates.
- **Requires mob `~> 0.9.8`**, the release that delivers that shape on both
  platforms. On older mob, iOS sends the same unlabelled map for an arrival
  and a tap, and Android drops taps for a registered screen.

## [0.1.3] - 2026-09-30

### Added

- **iOS silent-APNs host requirements** (MOB-271). The manifest now declares
  two more host_requirements, printed on every native deploy: the host
  Info.plist needs `UIBackgroundModes` `"remote-notification"` (generated by
  mob_new ≥ 0.6.1), and the App ID needs the Push Notifications capability in
  the Apple Developer Portal with a regenerated provisioning profile. Without
  these, `MobNotify.register_push/1` never gets a device token.

### Changed

- **Re-signed with plugin envelope v2** (MOB-287). mob_dev 0.7.2+ verifies
  this signature before evaluating the manifest. mob_dev 0.7.0 / 0.7.1 can't
  read v2 signatures and report this release as `invalid signature` —
  upgrade the host app to `{:mob_dev, "~> 0.7.2", only: :dev, runtime: false}`.
- **Docs: "Which plugin do I actually want?"** A new moduledoc section
  compares mob_notify with mob_push, mob_wake and mob_background. It also
  clarifies that "no Info.plist key needed" applies only to visible
  notifications, because silent APNs needs extra wiring (MOB-271).

### Fixed

- **Manifest `mob_version` matches the actual mob dep** (MOB-81). The
  plugin's `priv/mob_plugin.exs` pinned `mob_version: "~> 0.6"` while
  `mix.exs` pulled `{:mob, "~> 0.7"}`. Once a consumer ran
  `Manifest.validate/1`, the version-gate check would refuse the plugin
  outright — the plugin as shipped worked in host builds because that
  gate isn't invoked on every load. Bumped to `"~> 0.7"` to match the
  runtime dep.

## [0.1.2] - 2026-06-25

### Added

- Android boot re-arm: persisted schedules are re-armed by
  `MobNotifyBootReceiver` on `BOOT_COMPLETED`. Declares
  `SCHEDULE_EXACT_ALARM` + `RECEIVE_BOOT_COMPLETED` and a new host
  `<receiver>` requirement.

### Fixed

- Android: `notify_schedule` falls back to an inexact alarm when
  `SCHEDULE_EXACT_ALARM` isn't granted (previously threw, so the schedule
  silently failed).

## [0.1.1] - 2026-06-16

### Changed
- Signed release: the published package now carries a verified Ed25519
  signature (shared mob first-party key, regenerated in CI on every
  release). Generated apps trust it via `config :mob, :trusted_plugins`,
  so it clears the plugin signature gate without `acknowledge_unsafe_plugins`.

## [0.1.0] - 2026-06-12

Initial release. Local and push notifications for Mob apps — the device half, pairs with the server-side `mob_push` package.

- `MobNotify.schedule/2`, `cancel/2`, and `register_push/1`; delivery rides mob core.
- Extracted from mob core in the 0.7.0 plugin-extraction wave.
- Requires `mob ~> 0.7`.
